## 1. Определение проекта

### Название и назначение

**Quiet Water («Тихая вода»)** — студенческий *strategy-service*. Он стоит **снаружи** преподавательской платформы и на каждую закрытую свечу прогона отвечает одним решением: `BUY`, `SELL` или `HOLD`.

Сервис не биржа, не брокер и не личный кабинет студента. Он не исполняет заявки и не считает виртуальный портфель: это зона платформы. Его зона — **решение по одной свече** и соблюдение контракта событий.

### Торговая идея, которую проверяем

Гипотеза: на минутных свечах MOEX сырой сетап (разворот RSI) даёт много ложных входов. Имеет смысл торговать только если одновременно верны два условия:

1. на закрытом баре есть **ценовой сетап**;
2. в недавнем окне такие же сетапы **чаще отрабатывали**, чем нет (формула / счётчик успеха).

Пока данных мало, сервис **молчит**. Отсюда название: сначала тихая вода, удар — только после экзамена.

Алгоритм — **walk-forward**, три фазы на каждый инструмент отдельно:

| Фаза | Свечи | Что делает сервис | Сигнал наружу |
|---|---|---|---|
| A. Набор | `1 … N` | копит OHLC, считает формулу успеха на этом отрезке | только `HOLD` |
| B. Экзамен | `N+1 … N+K` | применяет формулу **без подгонки** и сверяет с фактом через `M` баров | только `HOLD` |
| C. Торги | дальше | скользит окном на одну свечу, пересчитывает score, торгует при проходном балле | `BUY` / `SELL` / `HOLD` |

Если live-score проседает, включается **circuit breaker**: снова `HOLD` и один новый экзамен на следующих `K` барах. Полный карантин `K` на каждом шаге фазы C **не** повторяется — иначе сервис почти никогда не выйдет в рынок.

**Сетап (детерминированное правило).** Mean-reversion на RSI(14):

- кандидат на `BUY`: RSI был ниже зоны перепроданности и закрытие текущей свечи выше предыдущего;
- кандидат на `SELL`: RSI был выше зоны перекупленности и закрытие ниже предыдущего;
- иначе сетапа нет → `HOLD`.

**Формула успеха.** Когда такой сетап уже встречался, смотрим цену через `M` свечей:

- BUY успешен, если `close[t+M] > close[t]`;
- SELL успешен, если `close[t+M] < close[t]`.

`successRate = успешные / W` по последним завершённым сетапам того же направления.

**Решение в фазе C:**

- есть сетап и `successRate ≥ T` и экзамен сдан → сторона сетапа;
- иначе → `HOLD`.

Стартовые параметры (все из переменных окружения, не из литералов в коде):

| Параметр | Смысл | Стартовое значение |
|---|---|---|
| `N` | длина окна обучения | 90 |
| `K` | длина экзамена | 45 |
| `M` | горизонт проверки успеха | 10 |
| `W` | сколько прошлых сетапов входит в score | 20 |
| `T` | пропускной балл | 0.55 |
| `RSI_PERIOD` | период RSI | 14 |
| `RSI_OVERSOLD` / `RSI_OVERBOUGHT` | зоны сетапа | 30 / 70 |

Успех бара `t` виден только на `t+M`. Последние `M` баров экзамена в зачёт не входят — иначе подглядывание в будущее.

**Звезда (не в критическом пути).** После отправки рекомендации фоновая поправка может слегка сдвинуть `confidence` **следующего** бара (например в пределах ±0.05). Сторону сделки (`BUY`/`SELL`) эта поправка не меняет. Численную корреляцию и hit-rate считает код сервиса, не языковая модель. Если модель не успела или недоступна — вклад равен нулю.

### Решаемая проблема

Платформа требует ответ на **каждую** закрытую свечу, с жёсткой связкой `runId` / `sourceEventId` / `instrument` / `sequenceNumber`. На 1-минутном realtime-прогоне нельзя:

- торговать каждый бар;
- подгонять формулу на тех же свечах, по которым идёт оценка;
- ставить в контур решения внешнюю LLM (латентность, недетерминизм, ломает будущую идемпотентность).

Нужен сервис, который умеет молчать, сдаёт экзамен на отложенном окне и остаётся воспроизводимым.

### Цели

1. Зафиксировать место сервиса: снаружи платформы, через Kafka, без UI.
2. Проверять одну гипотезу: сетап + пропускной балл, а не «модель угадывает рынок».
3. Выполнять учебный контракт: health, конфиг из окружения, контейнер, документация в Git.

### Основные задачи

1. Вести по каждому тикеру своё окно свечей и фазу (`LEARN` / `EXAM` / `TRADE` / `HALT`).
2. Считать RSI-сетап и скользящий `successRate` без заглядывания в будущее.
3. Публиковать одну рекомендацию на одну свечу в контракте платформы.
4. Отдавать `GET /health` без авторизации.
5. Читать секреты и пороги только из переменных окружения.

### Ожидаемый результат

- этот документ в Git;
- запускаемый каркас на Kotlin/Ktor: процесс поднимается, корректно завершается, `GET /health` отвечает HTTP 200;
- README, по которому можно собрать и запустить сервис без IDE;
- на следующих заданиях — подключение к Kafka и включение фаз A–C в боевой цикл.

Сейчас (задание 1) алгоритм в рантайме **ещё не торгует**: каркас поднимает HTTP и сообщает, что брокер не сконфигурирован (`DEGRADED`). Замысел алгоритма уже зафиксирован, чтобы следующие этапы его не ломали.

## 2. Границы проекта

### Входит в сервис

- приём закрытой свечи (когда появится Kafka) и хранение короткого окна в памяти процесса;
- расчёт сетапа, формулы успеха, фазы walk-forward;
- публикация торговой рекомендации;
- HTTP-диагностика `GET /health`;
- конфигурация через окружение;
- корректное завершение процесса (SIGTERM в контейнере).

### Заведомо снаружи

| Что | Кто отвечает |
|---|---|
| Запуск и остановка replay, выбор инструментов и таймфрейма | преподавательская платформа |
| Поставка рыночных данных | внешний поставщик платформы, не студент |
| Виртуальное исполнение, комиссии, портфель, группы | платформа |
| UI дашборда, практика, документация курса | платформа (`omsu.7bits.it`) |
| Реальные заявки брокеру | никто на этом стенде: платформа их не шлёт |
| Выдача логина Kafka, `secretKey`, имени топика | преподаватель |
| Сдача домашнего задания через форму в UI | платформы нет; сдача = Git + работающий сервис |
| Обучение LLM и онлайн-дообучение на текущем прогоне | не входит |

### Какие данные и решения контролирует сервис

Контролирует:

- своё решение `signal` и `confidence` на конкретную свечу;
- `suggestedQuantity` (0 на `HOLD` / warmup / экзамене, 1 на входе);
- `dataQuality` и текст `reason` / `metadata`;
- собственный `group.id` потребителя Kafka;
- готовность процесса (health).

Не контролирует:

- сойдётся ли окно консенсуса платформы;
- исполнят ли рекомендацию;
- как изменится стоимость портфеля;
- какие тикеры преподаватель включил в прогон.

### С кем взаимодействует

| Участник | Тип | Нужен уже в задании 1? |
|---|---|---|
| Студент-разработчик (`llnightll`) | человек | да: запуск, чтение логов |
| Преподаватель | человек, владелец стенда | да: выдаст брокер позже |
| Teacher Trading Platform | внешняя ИС | да как контрагент по смыслу; сеть — со следующего задания |
| Apache Kafka учебного стенда | брокер | заложен в границы, не подключён в каркасе |
| Языковая модель (звезда) | внешний HTTP API | только как опция следующих этапов |
| Браузер / curl | клиент health | да |

Пользователей «личного кабинета» у сервиса нет. Единственный машинный клиент HTTP — пробы liveness/readiness (преподаватель, Docker, сам разработчик).

## 3. Взаимодействия с внешними системами

### 3.1. Преподавательская платформа + Kafka

Платформа общается со студенческим сервисом **не по REST**, а событиями в защищённой Kafka.

**Известно по документации стенда (проверено 2026-10-11):**

- протокол: `SASL_SSL`, механизм `SCRAM-SHA-512`;
- параметры выдаёт преподаватель: `bootstrap.servers`, логин, пароль, имя топика свечей, при необходимости CA;
- активный прогон на стенде шёл в режиме `REALTIME`, таймфрейм `1m`, топик вида `market.candle.internal`;
- инструменты прогона: `SBER`, `T`, `TATN`, `GAZP`, `MAGN`, `MOEX`, `OZON`;
- исходящий тип события рекомендации: `strategy.recommendation.created`, `schemaVersion` `1.0`;
- связь свеча → рекомендация: `sourceEventId`, `runId`, `instrument`, `sequenceNumber`.

**Вход (когда брокер появится).** Событие закрытой свечи. Ожидаемые поля обёртки: `eventId`, `eventType`, `schemaVersion`, `occurredAt`, `correlationId`, `causationId`, `producer`, `payload` (инструмент, OHLC, `runId`, `sequenceNumber`).

**Выход.** Одна рекомендация на одну свечу. Обязательные поля `payload` по документации платформы: `recommendationId`, `sourceEventId`, `runId`, `secretKey`, `strategyId`, `accountId`, `groupId`, `sessionId`, `instrument`, `sequenceNumber`, `signal`, `confidence`, `suggestedQuantity`, `dataQuality`.

**Аутентификация.**

- к Kafka — логин/пароль SCRAM, TLS;
- `secretKey` в payload рекомендации — ключ, выданный преподавателем при регистрации сервиса;
- `GET /health` **без** авторизации (требование задания).

HTTP Basic на nginx (`realm="Teacher platform"`) защищает **учебный сайт**, не наш процесс. Сервис эти креды не использует.

**Ограничения.**

- внутренние адреса контейнеров платформы в код не зашивать;
- свой `group.id` у каждого экземпляра, иначе студенты делят партию сообщений;
- `auto.offset.reset=earliest` на первом подключении;
- повтор той же свечи должен дать то же решение (задел под идемпотентность семестра 2);
- ответ нужен быстро: LLM нельзя ставить до `produce`.

**Ошибки и деградация.**

| Ситуация | Поведение |
|---|---|
| Нет `KAFKA_BOOTSTRAP_SERVERS` / логина / топика | health: `kafka=DOWN`, общий статус `DEGRADED`, процесс жив |
| Брокер недоступен | health `DOWN`, переподключение; HTTP health всё равно 200 |
| Неполная последовательность свечей | `HOLD`, `confidence=0`, `dataQuality` не `OK` |
| Неизвестный инструмент | игнорирование или `HOLD` с причиной в `metadata` (уточняется) |
| Протухший `secretKey` | платформа отвергнет рекомендацию; сервис узнает это из события-результата, когда оно будет подключено |

### 3.2. HTTP health (этот репозиторий)

- метод: `GET /health`;
- авторизация: нет;
- успешный транспорт: **всегда HTTP 200**, даже если компоненты деградировали;
- тело: `status`, `service`, `version`, `components`.

Пример каркаса (брокер ещё не выдан):

```json
{
  "status": "DEGRADED",
  "service": "quiet-water",
  "version": "1.0.0",
  "components": {
    "kafka": {
      "status": "DOWN",
      "details": "broker is not configured"
    }
  }
}
```

### 3.3. Языковая модель (звезда, не в каркасе)

- направление: исходящий HTTPS после `produce`;
- вход модели: уже принятое решение и признаки бара, не «реши за меня»;
- выход: ограниченная поправка к следующему `confidence`;
- аутентификация: ключ API из окружения;
- ошибка / таймаут: поправка 0.

### Допущения и открытые вопросы

1. **Точное JSON-тело свечи** в этом репозитории ещё не законтрактовано кодом. Ориентир — глава «Событие закрытой свечи» на стенде. Открытый вопрос до задания про брокер.
2. Имя топика результата рекомендации и регистрационный heartbeat будут взяты из документации преподавателя, не угаданы.
3. `accountId` / `groupId` / `sessionId` выдаёт преподаватель; в `.env.example` стоят плейсхолдеры.
4. Платформа не шлёт реальные заявки — это факт документации, не гипотеза.
5. LLM не является критерием задания 1.

## 4. Состав решения

Только узлы, которые этому сервису **действительно** нужны. Отдельный пользовательский интерфейс и собственная СУБД в задании 1 не вводятся: нечем заполнять экран и нечего переживать между рестартами, пока нет задания на persistence.

| Компонент | Назначение | Зона ответственности |
|---|---|---|
| **Серверное приложение (Ktor / Netty)** | единственный исполняемый узел | HTTP health, жизненный цикл, позже — цикл «свеча → решение → produce» |
| **Модуль стратегии (в том же процессе)** | walk-forward, RSI-сетап, формула успеха | не знает про HTTP и Kafka-заголовки |
| **Брокер сообщений (учебная Kafka)** | транспорт событий | принадлежит стенду; наш сервис — клиент |
| **Конфигурация окружения** | пороги, адреса, секреты | двенадцать значений из env, ноль секретов в Git |
| **Контейнер Docker** | запуск без IDE | сборка JVM-образа, порт health, SIGTERM |
| **Проектный документ + README** | замысел и воспроизведение | живут в том же репозитории |

**Почему нет UI.** Наблюдение портфеля уже есть у платформы. Второй дашборд не входит в границы.

**Почему нет БД в каркасе.** Окно из `N+K` минутных свечей держится в памяти. Persistence — отдельное закрытое задание семестра 1 (`semester-1-persistence`). Когда его откроют, появится отдельный узел хранения, не раньше.

**Почему нет отдельного «ML-сервиса».** Формула успеха — обычная арифметика по OHLC. Выделенный inference-рантайм не нужен.

Схема:

```
[преподаватель / поставщик данных]
              │ свечи
              ▼
         [Kafka стенда]
          │           ▲
   consume│           │ produce рекомендация
          ▼           │
     [процесс quiet-water: стратегия + Ktor health]
          │
          └── GET /health  ← curl / Docker / преподаватель
```

## 5. Роли и ответственность

Оставлены только роли, без которых проект не объясняется. «Владелец продукта», «аналитик безопасности», «девопс отдельной компании» не вводим.

### Роли людей

| Роль | Кто | Ответственность |
|---|---|---|
| **Заказчик** | преподаватель курса | формулирует контракт событий, открывает задания, запускает прогон, смотрит портфели |
| **Разработчик** | студент `llnightll` | документ, каркас, алгоритм, секреты не в Git, сервис отвечает на свечи |
| **Оператор** | тот же студент в роли запускающего | собирает образ или `gradlew`, задаёт env, смотрит health и логи, останавливает процесс |
| **Администратор внешней системы** | администратор преподавательской платформы | Kafka, аккаунты, топики, ключи; наш репозиторий этим не управляет |
| **Владелец / поставщик рыночных данных** | поставщик стенда (не студент) | исторические или realtime свечи; к `quiet-water` напрямую не подключается |

### Роли машин

| Роль | Ответственность |
|---|---|
| Сервис `quiet-water` | решение и health |
| Платформа | поток свечей, проверка ключа, виртуальный портфель |
| Kafka | доставка, не бизнес-логика |

Роль «пользователь UI нашего сервиса» отсутствует: UI принадлежит платформе.
