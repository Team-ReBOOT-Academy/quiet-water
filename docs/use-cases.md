# Сценарии использования quiet-water

Рядом с [требованиями](requirements.md) и [задачами](tasks.md).
Сервис не показывает портфель и не выставляет биржевые заявки. Наблюдатель результата — преподаватель на платформе и студент по журналу и `GET /health`.

## UC-1. Проверка живучести

- Цель: понять, жив ли процесс и доступен ли брокер, не открывая Kafka.
- Участники: студент или преподаватель, сервис quiet-water.
- Предусловия: процесс запущен, порт HTTP известен.
- Событие запуска: `GET /` или `GET /health`.
- Основной ход: сервис собирает состояние Kafka и отвечает HTTP 200 с именем `quiet-water` и версией `1.0.0`.
- Альтернативы: нет адреса брокера — общий статус `DEGRADED`, компонент kafka `DOWN`, текст `broker is not configured`. Брокер задан, но соединение ещё не установлено — `broker is temporarily unavailable`. Соединение есть — общий статус `UP`.
- Наблюдаемый результат: JSON health. Процесс из-за недоступного брокера не завершается.
- Требования: FR-1, NFR-1, NFR-2. Задача 1.

## UC-2. Регистрация на платформе

- Цель: создать учётную запись студента через очередь, не через письмо и не через кнопку сайта.
- Участники: сервис, брокер Kafka, платформа.
- Предусловия: в окружении есть адрес брокера, ключ, секрет и свой `group.id`. Тема свечей может быть ещё пустой.
- Событие запуска: успешное подключение потребителя и производителя.
- Основной ход: сервис отправляет `account.registration.request` в одноимённую тему. В теле `accountName` — ФИО, `groupId` — учебная группа, `secretKey` — ключ, не секрет. Дальше сервис ждёт `account.registration.accepted` и запоминает `accountId`, `groupId` и `sessionId`.
- Альтернативы: `account.registration.rejected` или `accepted=false` — в журнал пишется причина, накопленные свечи не публикуются. Чужой ответ на общей теме игнорируется. Обрыв брокера не останавливает процесс: запрос повторяется, пока регистрация не завершена.
- Наблюдаемый результат: в журнале `registration.request`, затем `registration.accepted` либо `registration.rejected`. Секрет брокера и `secretKey` в журнал не попадают.
- Требования: FR-2, NFR-3, C-1. Задача 2.

## UC-3. Закрытая свеча превращается в одну рекомендацию HOLD

- Цель: подтвердить платформе, что сервис принял свечу и ответил контрактным событием, не открывая позицию.
- Участники: платформа, брокер, сервис, зарегистрированный студент.
- Предусловия: регистрация принята. Сообщение `market.candle.closed` прошло проверку структуры и обязательных полей. Эта `eventId` ещё не обрабатывалась.
- Событие запуска: запись в теме свечей, имя которой назвал преподаватель.
- Основной ход: сервис проверяет обёртку и payload, затем один раз вызывает обработку. На выходе ровно одно `strategy.recommendation.created`. `signal=HOLD`, `confidence=0`, `suggestedQuantity=0`. Связь со свечой: `sourceEventId`, `correlationId`, `causationId`, `runId`, `sequenceNumber`. В теле есть `studentId`, `strategyId`, идентификаторы принятой регистрации, `dataQuality`, `reason` и `processingTimeMs`.
- Альтернативы: регистрация ещё не принята — свеча копится и уходит одной рекомендацией после `accepted`. Повтор той же `eventId` вторую рекомендацию не создаёт.
- Наблюдаемый результат: в теме исходящих сообщений одна рекомендация HOLD на эту свечу. В журнале есть `candle.received` и `recommendation.published`.
- Требования: FR-3, FR-4, FR-5, FR-6, NFR-4. Задачи 3, 4 и 5.

## UC-4. Сообщение свечи не проходит проверку

- Цель: не строить рекомендацию по неполному или чужому по форме событию.
- Участники: платформа, брокер, сервис.
- Предусловия: процесс читает тему. Регистрация может быть уже принята.
- Событие запуска: сообщение с типом `market.candle.closed`, в котором нет обязательного поля обёртки или payload.
- Основной ход: проверка выполняется до окна свечей и до публикации. Обработка не начинается. Смещение сообщения фиксируется, чтение следующих записей продолжается.
- Альтернативы: тип события другой — запись игнорируется и рекомендацию не создаёт. Нечитаемый JSON даёт `message.skipped`.
- Наблюдаемый результат: `strategy.recommendation.created` для этой записи нет. В журнале причина пропуска называет отсутствующие поля и не содержит секрет.
- Требования: FR-3, NFR-2. Задача 3.

## UC-5. Публикация запрещена

- Цель: не отправлять рекомендацию, пока платформа не признала сервис либо уже отказала ему.
- Участники: сервис, платформа.
- Предусловия: свеча корректна.
- Событие запуска: свеча пришла в фазе ожидания регистрации или после отказа.
- Основной ход при отказе: причина уже записана, рекомендация не публикуется, в журнале `recommendation.withheld`.
- Альтернативы: брокер недоступен во время отправки — процесс остаётся жив, health показывает временную недоступность и соединение поднимается снова.
- Наблюдаемый результат: события `strategy.recommendation.created` нет, HTTP health по-прежнему 200.
- Требования: FR-2, FR-4, NFR-1, NFR-2. Задачи 1, 2 и 4.
